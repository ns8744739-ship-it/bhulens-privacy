1. Overview & Privacy Commitment

RudraGrid Technologies (“we”, “our”, or “us”) built BhuLens with local-first features. Map tiles, selected parcel lookups, optional account functions, purchases, and user-submitted Beta reports can involve off-device processing. Core map inspection, GPS field walks, and manual boundary measurements do not require account registration, but map and lookup requests may transmit geographic data to the selected map or public-data service.

Data not requested by a dedicated app feature: The inspected app source has no Aadhaar/PAN, contact-book, call-log, SMS, microphone, camera-capture, or advertising-ID feature. The app does allow an eligible Beta tester to select and upload an image with a report. Payment credentials are handled by Google Play, not collected by the app or publisher backend. No direct advertising, Firebase Analytics, or Crashlytics app dependency was found in the inspected declarations; this does not establish that third-party map or identity SDKs perform no provider-side processing.

3. Information Stored Locally on Your Device vs. Transmitted Over HTTPS

3.1 Local On-Device Data

The following data is stored exclusively inside your device’s private application sandbox:

  • Local SQLite Database (khetrekha.db): Saved revenue village bookmarks (villages table), cadastral overlay alignment parameters (cadastral_overlays table), and your user-traced manual boundary polygons, vertices, and area calculations (boundary_measurements table).
  • Map & WMS Tile Cache: Temporarily cached cadastral raster tiles and composite overlays stored in the app’s private cache directory for fast offline/low-connectivity field viewing.
  • Local preferences and credentials: Language/map preferences and local account state are kept in app storage. Authentication/session credentials use AndroidX Security Crypto and Android Keystore-backed APIs when the secure-storage path is available. The Room SQLite database itself is not encrypted by Room.
  • Backup settings: The app source sets android:allowBackup="false" and defines data-extraction exclusions. This is a source configuration statement, not a guarantee about every device/OEM transfer path.
  • Survey and saved data: Manually created boundary points/measurements and saved village/overlay data are stored locally; the inspected app/backend code does not implement cloud sync for those survey records.

3.2 Data That May Leave the Device

  • Maps and public cadastral lookup: Map rendering and user-selected parcel/plot lookups can transmit map coordinates, viewport/bounds, administrative codes, plot identifiers, and related query values to Google Maps/map endpoints and public Uttar Pradesh cadastral services, including upbhunaksha.gov.in. These transfers support map display and parcel lookup. The app code also contains other map-provider endpoints; the exact provider path depends on the selected map layer and release configuration. The inspected Esri identify caller currently takes a path that does not invoke its Esri request. Provider-side retention and SDK telemetry are not established by this app source.
  • Optional Google sign-in and account: If you choose Google sign-in, Google Identity/Credential Manager performs the credential flow and returns an ID token. The app sends that token and its generated installation ID (deviceInstallId) to the publisher backend. The backend verifies the token and stores the Google subject, verified email, display name, app/package/version, device model/OS, and session IP address/user-agent. The app request and backend schema do not include or store a profile-photo URL. Google’s sign-in documentation describes user consent to share profile information; it does not establish all provider-side processing or retention for this app.
  • Google Play Billing and purchases: The public client initializes Billing and can query products/purchases, restore, and start a purchase flow. When a purchase callback is received, the client can send purchase/product data, including a purchase token, to the publisher backend for verification. The backend gate is PLAY_BILLING_ENABLED; the checked-in default is false and a false runtime value rejects verification before persistence or a Google Publisher API call. The actual production value is unknown. The owner has decided to keep the current UI unchanged, keep the flag false, and defer the billing readiness review. Do not assume live product availability or successful verification. Google Play processes the purchase; the app/backend code does not collect card, bank, or UPI credentials.
  • Optional Beta reports and images: An eligible Beta tester may submit report text and optionally include diagnostics and an image attachment. Diagnostics can include app/version, device model/OS, app state/map type, counts, and entitlement state. A selected image is uploaded to the publisher backend; screenshots can contain personal or location information and are not automatically cleared of all such content. The attachment storage adapter supports local storage; the GCS adapter in source fails closed, and the deployed storage mode is not verified.

App-authored production API calls are configured to use HTTPS and the main Android network security configuration blocks cleartext traffic. This source-level setting does not independently verify every Google or other provider SDK connection. See Data Security Practices; universal in-transit encryption has not been independently verified.

5. Data Security Practices

  • App-authored network traffic: The main Android network security configuration blocks cleartext traffic, and app-authored remote API paths require HTTPS in release source configuration. The final merged release artifact and every provider SDK's internal transport were not independently inspected. We therefore do not claim that every data transfer used by every provider has been independently verified as encrypted in transit.
  • Local credentials: Authentication/session credentials use AndroidX Security Crypto and Android Keystore-backed APIs when the secure-storage path is available. The Room database is app-private but is not encrypted by Room.
  • Logging and report handling: Backend request logging is configured to redact sensitive keys and not serialize request bodies; authentication session records include IP address and user-agent. User-submitted report diagnostics have specific sanitization, but this does not remove sensitive information from images or guarantee that all free-form content is non-identifying.

6. Data Retention & Your Deletion Rights

The inspected source confirms that some server records remain after account deletion, but it does not establish their retention periods, backup purge schedule, or the legal/business basis for each retained category. No fixed deletion deadline or retention rationale is promised here; these require owner and legal review.

  • In-app account deletion: A signed-in user can open Profile & Account → Delete Account, enter the account email for confirmation, and submit the authenticated request. The backend clears the account email/display-name fields, replaces the Google subject with a tombstone, marks the account deleted, revokes session credentials, entitlements, and Beta membership, and clears FCM fields. On success, the app clears local authentication credentials and signed-in account/lease state.
  • Records retained after account deletion: The current backend flow does not delete linked device/install records and session history, purchase records (if created), village reservation/download records, bug reports/diagnostics and attachments, or security/audit history. The applicable retention periods, backup retention, and purge jobs have not been verified. This is an anonymizing soft delete, not complete/permanent erasure.
  • Local app data: Account deletion does not wipe the app-generated deviceInstallId, local Room database khetrekha.db, saved villages/overlays/boundaries, map caches, or other local preferences. Clear app storage or uninstall separately to remove local app data; this does not remove server-side records.
  • External deletion request: Read the Account & Data Deletion information page for the current in-app procedure and external-request status. That page is guidance only, not a web request form. A private external request channel and verified support address are not configured, so users who cannot access the app currently have no external request route. This does not yet satisfy Google Play's web deletion-request requirement.

Google Play requires an in-app deletion path and an external web resource that lets users request account deletion when the app supports account creation. See Google Play's account deletion requirements. Do not use the information page as the Console deletion URL until it provides a secure, functional request path.
